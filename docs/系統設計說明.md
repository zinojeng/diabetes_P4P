# 糖尿病 P14 / P7 收案資格判斷引擎——系統設計說明

給對象：接手串接 HIS/病歷系統的資訊工程師。
程式碼位置：`src/dm_eligibility/`。規格書位置：`spec/P14_rules_spec.md`、
`spec/P7_rules_spec.md`（本文件所有規則出處皆指向這兩份檔案）。

---

## 1. 問題背景：收案資格是一個「跨時間、跨就診次數」的狀態機問題

健保 P14（糖尿病照護管理）與 P7（糖尿病合併初期慢性腎臟病照護管理）的
「品質支付」給付邏輯，表面上看是一條條給付規則（例如「間隔七週」「年度
限3次」），但實際運作起來，它描述的是**單一病人隨時間推進、跨越多次
就診、跨越多個保險年度**的一段旅程：

```
未收案 → 新收案(P1407C) → 追蹤第1次 → 追蹤第2次 → 追蹤第3次 → 年度評估
       → （跨年度，計數器歸零，但終身總量持續累積）
       → 累積達第二階段門檻 → 進入第二階段（P1410C/P1411C）
       → 若同時滿足CKD收案 → 進入P7體系（P7001C/P7002C/P7003C）
       → 任一時點若符合結案條件 → 結案，1年內不得再收案
```

這與一般「單次請求→單次判斷」的 CRUD 邏輯完全不同，關鍵差異在於：

1. **同一個判斷（例如「P1408C 是否可申報」）的答案，取決於這個病人過去
   所有的申報歷史、就醫歷史、檢驗歷史**，不是只看「這一次就診的資料」
   就能判斷。
2. **同一組資料，會依「現在是哪一年」而變動判斷結果**（年度計數器在
   每年1月1日歸零，但終身累計計數器不歸零）。
3. **多個規則彼此有優先順序與互斥關係**（例如 P1408C 與 P7001C 同一次
   就診不可同時申報；P1409C/P1411C/P7002C 每年只能三選一），而且這些
   關係會隨著病人進入不同階段而改變。
4. **有些規則是「橫向」的**，不屬於病人自己的狀態轉移，而是掛在「醫師」
   這個維度上（醫師停權會讓他名下所有病人的申報全部失效），甚至有一條
   規則（180天強制檢驗排程）是完全獨立於收案狀態機之外、平行運作的。

若把這種問題硬編成「一堆 if-else 散落在各個 API/畫面裡」，會出現兩個
長期而言必然發生的後果：
- 同一條規則（例如「70天」）在系統裡出現在很多地方，健保署修法時一改
  就要到處找、到處改，改到一半漏改一處，就會產生本規格書列出的那種
  「文件說七週、系統還在跑七十天」的落差。
- 沒有一個地方可以清楚回答「這個病人現在到底在旅程的哪一站、下一步
  可以做什麼」，只能靠散落各處的 if 硬湊出答案，難以測試、難以追蹤
  誰改壞了什麼。

## 2. 為什麼用「狀態機 + 規則引擎」而不是散落各處的條件判斷

本專案的架構選擇：

- **狀態機**（概念層次，不是強制的程式碼 State 物件）：規格書 (d)/(e)
  節本身就是用狀態機文字描述整個流程，因此把這份文件轉譯成程式時，最
  忠實、最好維護的方式就是保留這個結構——每個照護碼的資格判斷函式，
  對應狀態機圖上的一段「轉移條件」。程式碼裡看得到 `check_p1407_...`
  → `check_p1408_...` → `check_p1409_...` 的順序，直接對照規格書的
  ASCII 狀態圖，日後接手的人不需要重新逆向工程規則從哪裡來。
- **規則引擎**（實作層次）：每個「轉移條件」拆成一個獨立、可單獨測試
  的純函式（輸入病人狀態快照，輸出「符合/不符合＋原因」），不與資料庫
  存取、UI、HIS 介接邏輯混在一起。這帶來三個直接的好處：
  1. **可測試**：不需要真的接資料庫、不需要跑完整個門診流程，就能用
     `tests/test_engine.py` 裡那種「捏造一個 PatientEnrollmentState」
     的方式，把「剛好70天 vs 剛好69天」這種邊界情境重現出來並斷言結果。
     這在散落各處的 if-else 架構下幾乎不可能做到（因為條件跟畫面渲染
     邏輯、SQL query 綁死在一起）。
  2. **可追溯**：每個規則函式的註解都標明對應規格書的章節與條文（例如
     `# 出處：P14 spec (a) A.2`），修法時工程師可以直接搜尋規格書的
     編號反查程式碼位置，而不是靠記憶或口耳相傳。
  3. **規則與資料分離**：所有「規格書沒寫死、屬於灰色地帶」的數字與
     開關，集中在 `models.EligibilityConfig` 一個資料類別裡，不散落在
     各個函式內部的魔術數字。修法或釐清待確認事項後，改一個欄位的
     預設值，不需要動到規則函式本身的邏輯結構。

## 3. 資料從哪裡來：HIS/病歷系統需提供的欄位

本引擎不做任何資料庫存取，呼叫端（HIS/病歷系統的介接層）需要在每次
評估前，組出一個 `PatientEnrollmentState`（定義於 `models.py`）快照，
內容包含：

| 資料類別 | 對應模型 | HIS 需提供欄位 | 對應規格書出處 |
|---|---|---|---|
| 就診紀錄 | `Encounter` | 就診日期、看診醫師代碼、診斷清單（ICD-10碼+是否主診斷）、用藥醫囑清單（ATC碼）、掛號診別代碼、是否已取消掛號 | P14 spec (b) B.1、(c) C.2 |
| 檢驗結果 | `LabResult` | 檢驗醫令碼（如09006C）、報告日期 | P14 spec (b) B.2~B.4、(c) C.2 |
| 已申報照護碼 | `CodeClaim` | 健保申報代碼（P1407C等）、申報日期、是否為團隊執行(80%點數) | P14 spec (c) C.3；本引擎統一用健保代碼，不用院內 P140801-03 細分碼（見第6節） |
| 結案紀錄 | `ClosureRecord` | 結案日期、結案原因 | P14 spec (a) A.6 |
| CKD分期評估 | `CKDAssessment` | 評估日期、eGFR、UPCR、UACR、是否為糖尿病患 | P7 spec (a) CKD-ENROLL-1/2 |
| VPN他院收案查詢結果 | `PatientEnrollmentState.vpn_other_institution_enrolled` | 是否已被他院收案中（**必須明確查詢後回填，不可留空當作「否」**） | P14 spec (a) A.1 排除條件 |
| Pre-ESRD轉診確認狀態 | `PatientEnrollmentState.pre_esrd_referral_confirmed` | 是否已經Pre-ESRD計畫院所確認收案 | P7 spec (d) P7003C |
| 病人年齡 | `PatientEnrollmentState.age_years` | 年齡（院內系統實作條件，非法規正文） | P14 spec (b) B.1 |
| 醫師資格/停權狀態 | `PhysicianStatus` | 追蹤率停權/登載不實停權的解除日期、是否具第二階段資格、是否具P70雙重資格 | P14 spec (a) A.6、P7 spec (a) |

**評估基準日** `as_of_date` 通常等於「當次就診日」——所有天數/年度計算
都以這一天為準。這代表每次門診就診（或批次重跑歷史資料）都應該重新組出
一份快照，而不是把 `PatientEnrollmentState` 當成一個長期存活、持續變動
的物件。

## 4. 「秘書口述的健保規定」與「資訊室系統邏輯」如何對應成可測試的程式規則

規格書 (c) 節本身已經把這個對應關係整理成一張表（秘書需求 → OS99系統
邏輯），本引擎進一步把這張表轉譯成第三層：**可測試的程式規則**。

對應方式：

1. **每一條規格書條文 → 一個具名函式或函式內的一個獨立判斷區塊**，並在
   程式碼註解標明出處（規格書章節代號，例如 `P14 spec (a) A.2`）。
2. **每一條「規格書沒寫清楚、兩份文件互相矛盾」的條文 → 一個
   `EligibilityConfig` 欄位**，欄位命名直接反映規則內容（例如
   `first_p1408_interval_days`），並在欄位註解寫明：
   - 對應規格書待釐清事項編號
   - 目前選擇的預設值
   - 為什麼選這個預設值（保守原則：寧可少放行、不多放行；資料缺漏時
     一律視為「不可判斷」而非臆測通過）
3. **每一條規則都有對應的 pytest 測試案例**，測試案例本身就是「這條
   規則的可執行規格」——例如「剛好49天可以、48天不行」直接對應規格書
   「至少須間隔七週」這句話的邊界語意，日後修改規則時，測試失敗即代表
   行為改變，不需要靠人工比對規格書才能發現。

這個三層對應（規格書條文 → 程式規則 → 測試案例）刻意設計成「規格書
怎麼寫，程式跟測試就怎麼命名、怎麼分段」，目的是讓不熟悉健保給付邏輯的
工程師，也能透過閱讀程式碼+測試回頭理解規則，而不需要每次都重新去讀
公文原文。

## 5. 未來健保署修法時的維護方式：規則設定與程式邏輯分離

架構上刻意把「會變動的數字/開關」與「不會變動的邏輯結構」分開：

- **不太會變的東西**（邏輯結構）：「新收案 → 第1次追蹤 → 第2次追蹤 →
  … → 年度評估」這種狀態轉移的順序關係、「年度計數器與終身計數器要分開
  算」這種資料模型設計、「品質監測是獨立於狀態機之外的平行規則」這種
  架構決策。這些寫死在 `rules_p14.py`/`rules_p7.py`/`engine.py` 的函式
  結構裡。
- **常會變的東西**（規則參數）：天數門檻（49天/70天/90天/180天）、
  年度次數上限、必要檢驗項目清單與有效期窗口、排除診別代碼清單。這些
  集中在：
  - `models.EligibilityConfig`：目前「不確定/有爭議」的規則開關。
  - `rules_p14.py` / `rules_p7.py` 檔案上方的模組常數（如
    `P1407_LAB_REQUIREMENTS_BASE`）：目前「規格書明確但未來可能修法」
    的規則參數。

**修法時的建議流程：**
1. 取得健保署正式函釋/新版附表，更新 `spec/P14_rules_spec.md` 或
   `spec/P7_rules_spec.md`（保留舊版本作為歷史對照，不要直接覆蓋——
   規格書本身建議逐字保留原文用語）。
2. 對照規格書更新內容，修改 `EligibilityConfig` 的預設值，或
   `rules_p14.py`/`rules_p7.py` 裡對應的模組常數/函式。
3. **新增或修改對應的測試案例**（尤其是邊界值測試），確認修改後的行為
   符合新規則的字面意義，且沒有意外影響到其他規則（跑一次
   `pytest tests/ -q` 確認全數通過）。
4. 若新規則有「生效日期」（例如某規則從某年某月某日才開始適用），現有
   引擎**尚未支援依歷史申報日期套用不同版本規則**（見第6節限制），
   需要額外設計版本化機制（例如把 `EligibilityConfig` 依生效日期做成
   一個查表函式）才能正確回溯判斷歷史案件。

這個分離的核心價值在於：**修法只需要動「資料」（設定值），不需要重新
設計「邏輯」（狀態機/函式結構）**，大幅降低每次修法的變更風險與測試
範圍。

## 6. 已知限制

- **未支援規則版本化／生效日期回溯判斷**：目前 `EligibilityConfig`
  只有一組「現行」設定值，無法依「這筆歷史申報案件發生在哪一天」自動
  套用當時有效的規則版本（例如70天門檻在106.05.01前後的差異）。若需要
  對歷史資料做稽核回溯，需另外設計版本化機制。
- **P4301C（CKD新收案）判斷為簡化實作**：因規格書並未提供CKD主診斷的
  ICD-10碼範圍（不像P14明確列出E08-E13），程式碼採用工程實作假設
  （N18，國際慣用慢性腎臟病碼），**此非規格書明文，串接HIS前務必與
  臨床端確認**（見 `models.EligibilityConfig.ckd_primary_diagnosis_icd10_prefixes`
  的註解）。
- **P4302C（CKD追蹤管理照護費）未實作**：P7規格書提及P4302C與P7001C
  互斥、合計上限等關聯規則，但P4302C本身的完整收案條件不在本次兩份
  規格書的核心範圍內，因此本引擎的互斥規則清單中，凡是需要
  「P4302C是否也符合資格」才能判斷的情境，目前只能略過（不會誤判為
  互斥，但也不會主動提示P4302C側的資訊）。
- **P4303C（CKD轉診照護獎勵費）未實作**：P7003C與P4303C互斥的規則
  同上，僅記錄需求未實作判斷。
- **同次就診多碼互斥僅止於「標記警告」，不自動選擇**：例如P1408C與
  P7001C同時符合資格時，引擎回傳兩者皆eligible=True並在
  `EligibilityReport.warnings` 中提示衝突，**不會**自動決定要留哪一個
  ——因規格書沒有明訂優先順序，貿然自動選擇可能與院內實際作業慣例不
  符，設計上刻意保守交由人工判斷。
- **42天「下次排程提醒」未實作**：規格書明確區分「70天/七週=可申報
  門檻」與「42天=提前提醒門檻」是兩套不同數字，本引擎只回答「現在
  是否可申報」，不負責提前排程提醒的功能（那是HIS門診排程模組的職責，
  不屬於收案資格判斷引擎）。
- **未實作醫師追蹤率<20%的自動計算**：`PhysicianStatus.tracking_rate_suspended_until`
  需由呼叫端另行計算並回填（本引擎只負責「已知停權期間內」的資格封鎖，
  不負責計算「當季追蹤率」本身，那需要另一套統計邏輯讀取整個醫師名下
  病人清單）。

## 7. 待釐清事項清單（彙整自兩份規格書）

以下逐條列出兩份規格書 (e)/(f) 節的待釐清事項，並註明本引擎目前的
保守處理方式（對應 `models.EligibilityConfig` 欄位或程式行為）。**這份
清單本身不是「已解決」的意思，而是「在等到正式確認前，程式暫時怎麼做」
的紀錄**，正式確認後應回頭更新對應的 config 預設值與本文件。

### P14 規格書待釐清事項

1. **P1407→首次P1408間隔「七週」是否已在OS99系統中生效？** 本引擎採
   現行法規基準49天（`EligibilityConfig.first_p1408_interval_days`），
   同時保留 `LEGACY_FIRST_P1408_INTERVAL_DAYS=70` 常數供需要比對院內
   舊邏輯時切換。
2. **42天「下次排程提醒」與70天/七週「實際可申報」間隔的關係。** 本引擎
   不實作排程提醒功能，只回答「現在是否可申報」，不受此問題影響，但
   若日後要做排程提醒模組，需另行確認42天數值的現行設定。
3. **P1407第一次收案是否仍適用「第一次就診免開藥」？** 本引擎預設
   `require_medication_on_earlier_visit=False`（不要求），採較新法規之
   寬鬆版本。
4. **P1409C「年度限1次」與「第二階段前需P1409累計≥2次」兩種計數概念。**
   本引擎在 `PatientEnrollmentState` 明確提供 `count_claims(code)`（終身
   累計，不帶year）與 `count_claims(code, year=...)`（年度計數）兩種
   查詢方法，`check_p1409_eligibility` 內部分別呼叫、不混用，並有專屬
   測試 `test_p1409_annual_counter_separate_from_lifetime_counter` 驗證。
5. **P1407收案排除診別代碼清單版本不一致（178碼）。** 本引擎預設採用
   較新的2023年版4碼清單（`EligibilityConfig.excluded_clinic_type_codes`），
   178碼的定義與移除原因仍待向資訊室/秘書確認。
6. **GA(醣化白蛋白)可否替代HbA1C。** 本引擎預設允許
   （`EligibilityConfig.allow_ga_as_hba1c_substitute=True`），因院內
   2023年版文件已採用，但健保署正式法規全文未提及，需另行確認正式
   依據。
7. **P1408C/P1409C健保申報碼與院內醫令碼(P140801等)的對應映射表。**
   本引擎刻意不依賴院內細分碼，一律以健保代碼+申報日期排序推導「第幾
   次」，繞開此對應問題，但若日後HIS只提供院內細分碼，介接層需自行
   完成映射轉換為健保代碼。
8. **品質監測(180天強制檢驗排程)的觸發對象範圍是否應與P14收案個案範圍
   一致。** 本引擎依規格書明文，將 `check_quality_monitoring` 實作為
   完全獨立於收案狀態機的規則（不檢查是否已有P1407C），與規格書「無論
   個案是否已進入P14收案狀態機」之敘述一致，此為規格書已明確表態之
   事項、非留待確認。
9. **缺乏明確的法規生效日期切點，無法依申報日期回溯判斷應適用哪個版本
   規則。** 本引擎目前無版本化機制，見第6節「已知限制」。
10. **P1410C/P1411C的完整支付規則記載較少。** 本引擎僅依規格書 (a) A.5
    明文之天數/次數規則實作 `check_p1410_eligibility`／
    `check_p1411_eligibility`，未涵蓋院內對等的系統阻擋細節（因規格書
    本身也未記載）。
11. **P1408C/P1409C是否已同步納入P7001C/P4302C等跨方案合計計數。** 本
    引擎依「現行法規基準」(`p7_core`) 預設 `enforce_cross_program_caps=True`，
    採跨代碼合計；院內OS99系統是否已同步實作是另一個問題，不影響本
    引擎邏輯本身的正確性。

### P7 規格書待釐清事項

1. **「須先有P4301才能收案P7」缺乏明文規則。** 本引擎預設
   `require_p4301_before_p7=True`，採規格書 (a) 節的建議結論。
2. **P7001C/P7002C是否適用「上次看診免OHA」規則。** 本引擎的P7規則不
   另外檢查OHA條件（因P7的前提是P1407C已收案，OHA條件已在P1407C收案
   當下判斷過），未重複或另訂P7專屬的OHA檢查，對應規格書「理論上可
   合理推論延續」的立場。
3. **代碼命名衝突（「P7」在舊文件中曾代表P1407C）。** 純文件層面問題，
   本引擎程式碼一律使用完整代碼（P1407C／P7001C等），不使用「P7」這種
   有歧義的簡稱，不受此問題影響。
4. **P7001C「7週」規則的異動溯源不明。** 本引擎依現行 `p7_core` 文字
   直接採用49天（`rules_p7.P7001_FIRST_INTERVAL_DAYS`），此數值本身
   在現行法規文件中並無爭議，僅「歷史上是否也曾變動過」不明，不影響
   現行判斷邏輯。
5. **42天「下次排程」規則是否適用於P70系列。** 同P14待釐清事項2，本
   引擎不實作排程提醒功能，不受影響。
6. **進入P7體系後對P1408C/P1409C的鎖定期是否適用。** 本引擎預設
   `lock_stage1_after_stage2_or_p7=True`，將「進入P7體系」與「進入
   第二階段」一併視為觸發1年鎖定的事件（保守：兩者都鎖）。
7. **`p14_schedule`文件內部疑似筆誤（P140801-P1408103）。** 純原始文件
   問題，不影響本引擎（本引擎不依賴院內細分碼，見P14待釐清事項7）。
8. **P1407C收案排除就診記錄名單版本差異（178碼）。** 同P14待釐清事項5，
   共用同一個 `EligibilityConfig.excluded_clinic_type_codes`。
9. **P7002C間隔起算基準「任一追蹤管理照護費」是否包含新收案本身。**
   本引擎預設 `p7002_interval_base_includes_new_enrollment=False`
   （字面解讀，僅計入追蹤管理照護費，不含新收案）。
10. **P7003C/P4303C的「Pre-ESRD計畫確認收案」介接方式未定。** 本引擎
    以 `PatientEnrollmentState.pre_esrd_referral_confirmed: Optional[bool]`
    表達此狀態，`None`（未知）一律視為不可申報，需由外部系統（人工
    回報或介接）明確回填 `True` 才會放行，絕不靜默假設為已確認。
